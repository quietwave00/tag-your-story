# #tagnote 커밋 스펙

## 1. 목적

이 문서는 `tag-note` 저장소에서 커밋과 브랜치를 일관되게 관리하기 위한 기준을 정한다.

목표:
- 변경 이력을 나중에 다시 읽기 쉽게 만든다.
- 백엔드 마이그레이션, React 마이그레이션, 인프라 변경을 서로 분리한다.
- 포트폴리오를 보는 사람이 커밋 흐름만 봐도 작업 의도를 이해할 수 있게 한다.

## 2. 브랜치 기본 구조

권장 브랜치:
- `main`: 배포 가능한 안정 버전
- `develop`: 다음 배포를 위한 통합 브랜치
- `feature/*`: 기능/리팩터링 작업 브랜치
- `release/*`: 배포 직전 안정화 브랜치
- `hotfix/*`: 운영 중 긴급 수정 브랜치

이번 프로젝트에서 자주 쓸 브랜치 예시:
- `feature/migration-backend`
- `feature/migration-react`
- `feature/backend-config-infra`

## 3. 커밋 컨벤션

기본 형식:

```text
type: 짧은 설명
```

권장 type:
- `feat`: 새 기능 추가
- `fix`: 버그 수정
- `refactor`: 동작 변화 없는 구조 개선
- `delete`: 파일 삭제
- `design`: UI/UX, 스타일, 레이아웃 변경
- `chore`: 빌드, 설정, 의존성, 잡무성 변경
- `test`: 테스트 추가/수정
- `docs`: 문서 수정
- `ci`: CI/CD 설정 변경
- `build`: 빌드 시스템 변경

선택 규칙:
- 한 커밋에는 한 가지 의도만 담는다.
- 기능, 설정, 테스트, 문서는 가능하면 분리한다.
- 이름만 보고도 대략 무엇을 바꿨는지 알 수 있게 쓴다.

## 4. 커밋 메시지 작성 규칙

기본 원칙:
- 첫 글자는 소문자 타입을 사용한다.
- 설명은 짧고 직접적으로 쓴다.
- 과장된 표현은 피한다.
- 한글 메시지로 작성

권장 예시:
- `feat: 파일 저장소 추상화 추가`
- `fix: 토큰 만료 시 재발급 처리 수정`
- `refactor: 댓글 서비스 책임 분리`
- `design: 게시글 상세 화면 여백 조정`
- `chore: gradle wrapper 버전 갱신`
- `test: 좋아요 락 테스트 보강`
- `docs: 브랜치 전략 문서 추가`

비권장 예시:
- `fix stuff`
- `update`
- `test`
- `temp`
- `backup`

## 5. 브랜치와 커밋을 나누는 기준

브랜치를 나눠야 하는 경우:
- 백엔드와 프론트엔드가 함께 바뀌는 경우
- 설정/인프라 변경과 기능 구현이 섞이는 경우
- 큰 마이그레이션 작업으로 한 번에 읽기 어려운 경우

커밋을 나눠야 하는 경우:
- 코드 변경과 테스트 변경이 독립적일 때
- 기능 구현과 문서 수정이 분리될 때
- 리팩터링과 동작 변경이 섞일 때

## 6. 작업 흐름

권장 흐름:

1. `develop`에서 작업 브랜치를 딴다.
2. 작업 단위에 맞게 작은 커밋으로 나눈다.
3. 브랜치 내부에서 우선 동작을 맞춘다.
4. 테스트와 검증을 끝낸 뒤 `develop`에 merge 한다.
5. 필요하면 `release/*`로 안정화한다.
6. 배포 후 `main`에 반영하고 tag를 남긴다.

## 7. 마이그레이션 작업 가이드

현재 프로젝트에서는 마이그레이션 작업을 다음처럼 나누는 것을 기본으로 한다.

- `feature/migration-server`
  - 서버, 배치, 설정, 인프라 관련 변경
- `feature/migration-client`
  - React 앱, 화면, 프론트 자산 관련 변경

추가로 분리할 수 있는 경우:
- `feature/backend-file-storage`
- `feature/backend-security`
- `feature/backend-batch`
- `feature/frontend-auth`

## 8. 리뷰 전 체크 항목

커밋 또는 merge 전에 확인할 것:
- 커밋 메시지가 `type: 설명` 형식을 따르는지
- 한 커밋에 주제가 너무 많지 않은지
- staged / unstaged 변경이 의도대로 나뉘어 있는지
- 테스트나 빌드 확인이 필요한 변경인지
- 문서나 설정이 필요하면 함께 반영했는지
